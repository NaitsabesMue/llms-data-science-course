\section{Specify the Task and Supply Context}

\begin{frame}{Start with a Question We Can Check}
  \begin{block}{The assignment}
    Customers are leaving. Does observed churn differ by contract type?
  \end{block}
  \textbf{Churn} means that a customer leaves. In our data, \texttt{churn=1} means the customer left; \texttt{churn=0} means they did not.
  \par\vspace{0.5em}
  For each contract type, we want:
  \begin{itemize}
    \item the number of customers and the number who left;
    \item the fraction who left: the number who left divided by the total number of customers with that contract type.
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{A Small Dataset We Can Check by Hand}
  \begin{columns}[T,onlytextwidth]
    \begin{column}{0.49\linewidth}
      \small \texttt{csv\_text} is a Python string containing comma-separated values (CSV): six customers, one row each.
\begin{lstlisting}[language=Python,commentstyle=\ttfamily\color{AMU_dk1}]
csv_text = """contract_type,churn
month-to-month,1
month-to-month,0
month-to-month,1
one-year,0
one-year,1
two-year,0
"""
\end{lstlisting}
    \end{column}
    \begin{column}{0.46\linewidth}
      \small \textbf{Context we must supply}
      \begin{itemize}
        \item What a row represents.
        \item What the columns and values mean.
        \item Which rows belong in each calculation.
      \end{itemize}
      \textbf{Check now}: among the three month-to-month customers, how many left?
    \end{column}
  \end{columns}
  \par\vspace{0.3em}
  \small Later, Python will analyse the lab's 600-row synthetic dataset. We use these six rows first to make errors visible.
\end{frame}

\begin{frame}[fragile]{Turn the Question into an Explicit Request}
  \small \texttt{task\_text} is a Python string describing the user's task. This variable name is our choice; it is not an API field.
\begin{lstlisting}[language=Python,commentstyle=\ttfamily\color{AMU_dk1}]
task_text = """Compare churn by contract type.
Each row is one customer; churn: 0 = stayed, 1 = left.
For each type, report n_customers (group size)
and n_churn (customers who left).
churn_rate = n_churn / n_customers, from 0 to 1.
Return a table. Report observed differences only."""
\end{lstlisting}
  \small This specifies the \textbf{task}, relevant \textbf{context}, required \textbf{output} and a limit on the \textbf{conclusion}.
  \par\vspace{0.4em}
  Start with what the task needs. Add instructions or examples to address failures you actually observe.
  \note{A fixed role/task/format template is not a guarantee of quality. Examples can clarify a convention, as the JSON example below does for fractions versus percentages. An extra prompt-writing call is not mandatory. References: https://ai.google.dev/gemini-api/docs/prompting-strategies and https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents.}
\end{frame}

\begin{frame}{Why Separate System Instructions from the User Message?}
  \small Imagine an analysis application used for different datasets and questions. We separate the application's guidance from the user's particular task.
  \par\vspace{0.5em}
  \begin{columns}[T,onlytextwidth]
    \begin{column}{0.47\linewidth}
      \textbf{System instruction}
      \begin{block}{Set by the application}
        \small Use supplied evidence. State missing information. Distinguish observation from causation.
      \end{block}
    \end{column}
    \begin{column}{0.47\linewidth}
      \textbf{User message}
      \begin{block}{The task and its data}
        \small Compare churn by contract type using the six CSV rows and the definitions we just supplied.
      \end{block}
    \end{column}
  \end{columns}
  \vspace{0.5em}
  \small The application can reuse the guidance while the user's task and data change.
  \par\vspace{0.4em}
  \textbf{In our example, both parts are sent together on every call.} The system instruction is optional; one user message is enough for a simple request.
  \note{This is a distinction between who supplies instructions, not between permanent and temporary memory. Reuse is an application design choice: a system instruction can also change between calls. Our standalone generate_content calls do not retain earlier instructions automatically. The API fields identify the parts; typing System: in plain text does not create a system instruction. The cat persona remains a short lab demonstration of style rather than evidence of correctness. System instructions alone do not enforce permissions.}
\end{frame}

\begin{frame}[fragile]{Connect Python to a Hosted Model}
  \small An \textbf{API} is an interface through which our Python program sends a request to a service and receives a response.
\begin{lstlisting}[language=Python]

  \begin{itemize}
    \item \texttt{client} is the object we use to contact the service.
    \item \texttt{model\_name} fixes one common model for the course.
    \item The model runs at the provider; we do not download its weights here.
  \end{itemize}
  \note{Install google-genai and python-dotenv as in the lab. Keep keys local and never print them. Calls use account quota and may incur charges. Retain the notebook's generate_content interface rather than changing APIs during the lecture. Source: https://github.com/googleapis/python-genai.}
\end{frame}

\begin{frame}[fragile]{Build the User Message}
\begin{lstlisting}[language=Python,commentstyle=\ttfamily\color{AMU_dk1}]
task_text = """Compare churn by contract type.
Each row is one customer; churn: 0 = stayed, 1 = left.
For each type, report n_customers (group size)
and n_churn (customers who left).
churn_rate = n_churn / n_customers, from 0 to 1.
Return a table. Report observed differences only."""

csv_text = """contract_type,churn
month-to-month,1
month-to-month,0
month-to-month,1
one-year,0
one-year,1
two-year,0
"""
prompt = task_text + "\n\nData (CSV):\n" + csv_text
\end{lstlisting}
\end{frame}

\begin{frame}[fragile]{Send the Message and Read the Table Reply}
\begin{lstlisting}[language=Python]
config = types.GenerateContentConfig(
    system_instruction=(
        "Use supplied evidence. State missing information. "
        "Distinguish observation from causation."))
response = client.models.generate_content(
    model=model_name, contents=prompt, config=config,
)
print(response.text)
\end{lstlisting}
  \small This call sends the system instruction through \texttt{config}, and the user message (task plus six CSV rows) through \texttt{contents=prompt}.
  \par\vspace{0.5em}
  \texttt{response.text} contains the model's table reply as a Python string. \texttt{print(response.text)} displays that reply.
\end{frame}

\section{Read and Validate the Output}

\begin{frame}[fragile]{What Does the Table Reply Look Like?}
\begin{lstlisting}[language=Python]
print(type(response.text))
print(response.text)
\end{lstlisting}
  \small A possible output, illustrated with our six rows:
\begin{lstlisting}[language={},columns=fixed]
<class 'str'>
| contract_type  | n_customers | n_churn | churn_rate |
|----------------|-------------|---------|------------|
| month-to-month | 3           | 2       | 0.6667     |
| one-year       | 2           | 1       | 0.5        |
| two-year       | 1           | 0       | 0.0        |
\end{lstlisting}
  \small \texttt{str} means a Python string. The table is written using characters inside that string; the bars separate its columns.
  \par\vspace{0.5em}
  We can read the displayed table, but Python needs to extract its values before using them in calculations. Next, we request a format designed for that step.
  \note{This is an illustrative response, not an observed live model output. Actual wording and formatting vary. The table uses Markdown notation; a chat application may render that notation as a formatted table, while print displays the text. Python can parse several tabular text formats; JSON is the next example here, not the only possible choice. No pandas DataFrame is created automatically by this model call.}
\end{frame}

\begin{frame}[fragile]{Choose an Output Your Program Can Read}
  \small For the next call, ask for the same results as \textbf{JSON text}. JSON is a text format for objects with named fields, lists and values.
\begin{lstlisting}[language={}]
[
  {"contract_type": "month-to-month",
   "n_customers": 3, "n_churn": 2,
   "churn_rate": 0.6667}
]
\end{lstlisting}
  \small Illustrative output for \textbf{one group}; the complete answer needs all three groups.
  \begin{itemize}
    \item Outer brackets hold a list; braces hold an object.
    \item \texttt{contract\_type} is a string; counts and rates are numbers.
    \item An example clarifies the convention: \texttt{0.6667} is a fraction, not \texttt{66.67} percent.
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{Parsing Is Only the First Check}
\begin{lstlisting}[language=Python]
import json
json_prompt = prompt.replace("Return a table.", "Return a JSON list.")
json_response = client.models.generate_content(
    model=model_name, contents=json_prompt, config=config,
)
rows = json.loads(json_response.text)
\end{lstlisting}
  \small We expect a Python list of dictionaries, one per contract type.
  \par\vspace{0.3em}
  \renewcommand{\arraystretch}{1.2}
  \begin{tabular}{@{}p{2.2cm}p{4.7cm}p{5.2cm}@{}}
    \toprule
    \textbf{Check} & \textbf{Question} & \textbf{How we check} \\
    \midrule
    Syntax & Can Python read the JSON? & \texttt{json.loads()} \\
    Structure & Correct fields and types? & Validate against a schema. \\
    Content & Correct counts and rates? & Recompute from the data. \\
    \bottomrule
  \end{tabular}
  \par\vspace{0.4em}
  \small A \textbf{schema} defines required fields, their types and limits.
  \note{json.loads can return several Python types, so check the outer structure too. JSONDecodeError, missing fields and wrong numbers are separate failures. Do not silently exclude failed calls from evaluation. Source: https://docs.python.org/3/library/json.html.}
\end{frame}

\begin{frame}[fragile]{Structured Output: First Define the Required JSON}
  \small \textbf{Structured output is an API feature.} We supply a \textbf{JSON Schema}: a specification of the response's structure, fields and types.
\begin{lstlisting}[language=Python]
row_schema = {
    "type": "object",
    "properties": {
        "contract_type": {"type": "string"},
        "n_customers": {"type": "integer", "minimum": 1},
        "n_churn": {"type": "integer", "minimum": 0},
        "churn_rate": {"type": "number", "minimum": 0, "maximum": 1},
    },
    "required": ["contract_type", "n_customers", "n_churn", "churn_rate"],
}
result_schema = {"type": "array", "items": row_schema}
\end{lstlisting}
  \small \texttt{properties} defines the fields; \texttt{required} lists mandatory fields. \texttt{array} means a list, whose items must follow \texttt{row\_schema}.
  \note{The schema is a Python dictionary written using standard JSON Schema keywords. Its object type describes one group; the outer array describes all groups. The bounds constrain counts and rates, but do not establish that a count matches the input or that every group is returned. Sources: https://ai.google.dev/gemini-api/docs/structured-output and https://github.com/googleapis/python-genai.}
\end{frame}

\begin{frame}[fragile]{Enable Structured Output in the API Call}
\begin{lstlisting}[language=Python]
json_config = types.GenerateContentConfig(
    system_instruction=config.system_instruction,
    response_mime_type="application/json",
    response_json_schema=result_schema,
)
json_response = client.models.generate_content(
    model=model_name, contents=json_prompt, config=json_config,
)
rows = json.loads(json_response.text)
\end{lstlisting}
  \begin{itemize}
    \item \texttt{response\_mime\_type} selects JSON as the response format.
    \item \texttt{response\_json\_schema} supplies the required structure and types.
  \end{itemize}
  \small The reply is still JSON text. \texttt{json.loads()} converts it to Python objects.
  \par\vspace{0.4em}
  \texttt{0.99} would pass the range check (0 to 1), however, the correct rate is $2/3 \approx 0.667$.
\end{frame}

\begin{frame}{Docker: Package and Run Applications Independently}
  \small \textbf{Docker} packages an application and the software it needs into an \textbf{image}: for example, Python, libraries and system tools. A \textbf{container} runs that image with its own files and processes.
  \begin{center}
  \begin{tikzpicture}
    \node[taskbox,text width=4.3cm,fill=AMU_acc5!30] (analysis) at (-2.6,0) {Analysis container\\Python + pandas\\System tools};
    \node[taskbox,text width=4.3cm,fill=AMU_dk2!10] (dashboard) at (2.6,0) {Dashboard container\\Python + web libraries\\System tools};
    \node[draw=AMU_dk2,rounded corners=3pt,fill=AMU_lt2!55,
      text width=9.8cm,align=center,inner sep=5pt,font=\small]
      (kernel) at (0,-1.2) {Shared Linux kernel (the core of the operating system)};
    \draw[thick,draw=AMU_acc1] (analysis.south) -- (analysis.south |- kernel.north);
    \draw[thick,draw=AMU_acc1] (dashboard.south) -- (dashboard.south |- kernel.north);
  \end{tikzpicture}
  \end{center}
  \begin{itemize}
    \item \textbf{Modularity}: run and update each application separately.
    \item \textbf{Reproducibility}: reuse the same image to keep the software environment consistent across runs and computers.
  \end{itemize}
  \par\vspace{0.3em}
  \small A \texttt{venv} separates Python packages. Docker also packages system tools and provides separate files and processes for each application.
  \note{This slide explains Docker's general purpose before applying it to generated code. The two containers illustrate separate application environments; the current lab starts only an analysis container. Containers share a kernel rather than each booting an entire operating system. On macOS and Windows, Docker Desktop supplies a Linux virtual machine whose kernel is shared by these Linux containers. Reusing an image controls the software environment, not randomness, hardware differences or every source of variation in results. Sources: https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/, https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/ and https://docs.python.org/3/library/venv.html.}
\end{frame}

\begin{frame}{Ask an LLM to Review the Plot}
  \small We just inspected the plot ourselves and requested a change. We can automate this review with another LLM call.
  \par\vspace{0.4em}
  Send the task, previous code, printed table and actual PNG image to a model that accepts images:
  \begin{center}
  \begin{tikzpicture}[node distance=0.5cm]
    \node[taskbox,fill=AMU_lt2!55] (input) {Task + code\\Table + plot image};
    \node[taskbox,fill=AMU_acc5!30,right=of input] (review) {Another LLM call\\Review the output};
    \node[taskbox,fill=AMU_dk2!10,right=of review] (feedback) {Accept the plot\\or request changes};
    \draw[taskarrow] (input) -- (review);
    \draw[taskarrow] (review) -- (feedback);
  \end{tikzpicture}
  \end{center}
  \begin{block}{The review request}
    \small Compare the plot with the table. Are the axes and units clear? Is every group labelled, including zero values? Return specific changes if needed; otherwise accept the plot.
  \end{block}
  \small Python checks the numbers independently. The LLM reviews readability and consistency with the table; its feedback can trigger a new code-generation call.
  \note{This is another API request, not a new trained model: the same model may handle both code generation and review if it accepts images. The API content must contain the actual PNG as an image part alongside the task, table and criteria. With the existing Google SDK this can use types.Part.from_bytes(data=plot_bytes, mime_type='image/png') inside contents. A plot filename alone does not supply the image. For an automated decision, validate an accept/revise response using the structured-output approach introduced earlier. This review call is a proposed extension, not a captured API response. Independent arithmetic checks remain separate from model judgement. Source: https://github.com/googleapis/python-genai and https://ai.google.dev/gemini-api/docs/image-understanding.}
\end{frame}

\begin{frame}{From Our Review to an Agent Loop}
  \small In an \textbf{agent loop}, the model uses returned results to choose its next action: revise the code, run again or accept the result.
  \par\vspace{0.4em}
  We implement this loop in Week 5: the program runs the code and returns results.
  \begin{center}
  \begin{tikzpicture}[node distance=0.55cm]
    \node[taskbox,fill=AMU_acc5!30] (model) {LLM review\\Choose next step};
    \node[taskbox,fill=AMU_dk2!10,right=of model] (run) {Run Python\\Check numbers};
    \node[taskbox,fill=AMU_lt2!55,right=of run] (output) {Table + plot\\+ check results};
    \draw[taskarrow] (model) -- node[above,font=\footnotesize] {Run} (run);
    \draw[taskarrow] (run) -- (output);
    \draw[taskarrow] (output.north) -- ++(0,0.45) -| (model.north);
    \draw[taskarrow] (model.south) -- ++(0,-0.45)
      node[below,font=\footnotesize] {Accept this run};
  \end{tikzpicture}
  \end{center}
  \small \textbf{After the six-row check passes}: run the same code on the full dataset and check that output too.
  \par\vspace{0.4em}
  \textbf{Finish} when the full analysis passes the numerical checks and meets the presentation requirements. Limit revisions, for example to three attempts; unresolved issues go to human review.
  \note{The extra review call is one step; agency comes from allowing a model to choose subsequent actions using results, rather than treating a second call alone as an agent. A fixed evaluator-optimizer sequence can also be implemented as a workflow. The agent extension permits model decisions to revise code, rerun it or finish, while our program enforces execution permissions, independent checks and limits. The current example demonstrates the manual cycle; Week 5 implements control of actions and traces. Finishing on the toy case is not completion of the full-data task. Reference: https://www.anthropic.com/engineering/building-effective-agents.}
\end{frame}
