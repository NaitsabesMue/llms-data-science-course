\begin{frame}[fragile]{Load the Tokenizer and Model from One Version}
  \small A saved version ID identifies the files from the previous slide: \textbf{tokenizer files, trained weights and configuration}.
  \par\vspace{0.3em}
  The loading functions call this version \texttt{revision}.
  \begin{lstlisting}[language=Python]
from huggingface_hub import HfApi
from transformers import AutoTokenizer, AutoModelForSequenceClassification
name = "distilbert/distilbert-base-uncased-finetuned-sst-2-english"
# Look up the current version ID. Save it to reuse this version later.
version_id = HfApi().model_info(name).sha
# Load the tokenizer: text <-> token IDs.
tokenizer = AutoTokenizer.from_pretrained(name, revision=version_id)
# Load the classifier: configuration + trained weights.
model = AutoModelForSequenceClassification.from_pretrained(
    name, revision=version_id)
  \end{lstlisting}
  \small \texttt{tokenizer} prepares the text; it does not predict sentiment. \texttt{model} makes that prediction. Neither loading call runs a prediction yet.
  \note{The previous variable tok referred only to the tokenizer. Use the full name here. Both calls use the same model page and version ID. Resolving the current ID again on a later day may select newer files; reuse the saved ID to repeat this version. Package versions, data and settings must also be recorded for the experiment.}
\end{frame}

\begin{frame}[fragile]{Model Files Can Also Include Python Code}
  \small In our example, the installed \texttt{transformers} library already knows how to run DistilBERT. We download its trained weights and settings.
  \par\vspace{0.4em}
  Some Hub models also supply their own Python code. Loading the trained weights and running that code are \textbf{two separate choices}.
  \par\vspace{0.5em}
  \begin{columns}[T,onlytextwidth]
    \begin{column}{0.47\linewidth}
      \textbf{How are the weights stored?}
      \par\vspace{0.3em}
      \texttt{safetensors} is a file format for storing the trained weights. Reading this format does not execute Python code from the weight file.
    \end{column}
    \begin{column}{0.49\linewidth}
      \textbf{May the model run extra code?}
      \par\vspace{0.3em}
      \texttt{trust\_remote\_code=True} allows Python code from the model's Hub repository to run on your machine.
      \par\vspace{0.3em}
      Our DistilBERT example does not need it.
    \end{column}
  \end{columns}
  \par\vspace{0.5em}
  \begin{lstlisting}[language=Python]
model = AutoModelForSequenceClassification.from_pretrained(
    name, revision=version_id,
    use_safetensors=True,    # Read weights in the safetensors format.
    trust_remote_code=False)  # Do not run extra code from the Hub.
  \end{lstlisting}
  \note{The two options answer different questions. A safetensors weight file does not make separately downloaded Python code safe. Do not introduce pickle or deserialization terminology. If a later model requires custom code, examine that code and its source before enabling it. These flags do not replace the configuration or tokenizer.}
\end{frame}

\begin{frame}[fragile]{Our First Call: Classify One Review}
  \small We specify the task and the trained model to use:
  \begin{lstlisting}[language=Python]
from transformers import pipeline
classifier = pipeline(
    "text-classification",
    model="distilbert/distilbert-base-uncased-finetuned-sst-2-english",
    device="cpu")

  \end{lstlisting}
  \begin{itemize}
    \item \texttt{classifier} holds the pipeline: tokenizer, model and result handling.
    \item \texttt{device="cpu"} runs the calculation on the computer's main processor.
    \item The result contains a \texttt{label} and its \texttt{score}; inspect both in the lab.
  \end{itemize}
  \small Try ``This movie was terrible'' and ``The movie lasts two hours.'' The model must choose positive or negative: it has no neutral label.

\end{frame}

\begin{frame}{From Logits to Sentiment Probabilities}
  \small
  \setlength{\abovedisplayskip}{4pt}\setlength{\belowdisplayskip}{4pt}
  \setlength{\abovedisplayshortskip}{2pt}\setlength{\belowdisplayshortskip}{4pt}
  The model turns the review into a vector $h$. Its final layer calculates two scores:
  \par\vspace{0.5em}
  \begin{columns}[T,onlytextwidth]
    \begin{column}{0.48\linewidth}
      \textbf{1. Calculate the raw scores: logits}
      \[
        z_c = w_c^{\mathsf T}h + b_c
      \]
      \small $c$ is a class: negative or positive.\\
      $w_c$: learned weight vector.\\
      $b_c$: bias, a constant learned during training.
      \par\vspace{0.4em}
      Logits can be negative. They are scores, not probabilities.
    \end{column}
    \begin{column}{0.48\linewidth}
      \textbf{2. Convert the logits: softmax}
      \[
        p_c = \frac{e^{z_c}}{e^{z_{\mathrm{neg}}}+e^{z_{\mathrm{pos}}}}
      \]
      \small Exponentiation makes both values positive. Dividing by their sum makes the probabilities add up to one.
      \par\vspace{0.4em}
      The pipeline chooses the class with the larger $p_c$ and returns that value as its \texttt{score}.
    \end{column}
  \end{columns}
  \par\vspace{0.2em}
  \textbf{Illustrative example}: $z_{\mathrm{neg}}=-1$, $z_{\mathrm{pos}}=2$.
  \[
    p_{\mathrm{pos}} = \frac{e^2}{e^{-1}+e^2}\approx 0.953,
    \qquad p_{\mathrm{neg}}\approx 0.047
  \]
  \small Prediction: \texttt{POSITIVE}. A score of $0.953$ does not establish a $95.3\%$ chance that the sentence expresses positive sentiment.
  \note{h denotes the vector actually entering the final linear classifier, after any preceding processing; do not imply that every model directly classifies an unprocessed token embedding. In this DistilBERT checkpoint a learned pre-classifier and activation precede the final layer. w and b are loaded trained weights, not calculated anew from the review. This formula produces logits; the term does not mean taking a logarithm of the input. Softmax([-1,2]) is approximately [0.0474,0.9526]. Toy scores are chosen for explanation. Real score-to-label order comes from config.id2label.}
\end{frame}

\begin{frame}[fragile]{Inside the Pipeline (1/2): Text to Raw Scores}
  \small Inspect the pipeline step by step, using the tokenizer and model loaded on slide 7.
  \[
    \text{Text}\xrightarrow{\text{tokenizer}}\text{Token IDs}
    \xrightarrow{\text{model}}\text{Logits}
  \]
  \begin{lstlisting}[language=Python]
import torch
text = "I loved this movie"  # 1. Supply the text.
inputs = tokenizer(text, return_tensors="pt")  # 2. Tokenize.
print("Token IDs:", inputs["input_ids"])
model.eval()  # Set training=False on the model and its layers.
with torch.inference_mode():  # 3. Run the trained model.
    logits = model(**inputs).logits  # ** passes dictionary entries by name.
print("Raw scores:", logits)
  \end{lstlisting}
  \small \texttt{torch} is PyTorch, the library running the numerical calculations. \texttt{return\_tensors="pt"} returns PyTorch arrays, called tensors.
  \par\vspace{0.3em}
  \texttt{eval()} disables dropout: the random removal of activations used during training. \texttt{inference\_mode()} disables gradient tracking. Neither changes the learned weights.
  \note{We inspect the whole pipeline, not individual Transformer layers. Steps 1-3 expose the text, tokenizer inputs and model output; steps 4-5 follow on the next slide. model(**inputs) unpacks the tokenizer's input dictionary into named arguments; this model calculation is one forward pass. For this tokenizer, it is equivalent to model(input_ids=inputs['input_ids'], attention_mask=inputs['attention_mask']). The tokenizer also returns a padding mask, explained with batching later. eval() calls train(False), setting the training flag on the model and its submodules; dropout stops randomly zeroing activations. Hugging Face from_pretrained() already sets evaluation mode by default, so this explicit call documents and ensures the intended mode. It does not disable gradient tracking; inference_mode() handles that separately. Compare against classifier(text) using the same model version.}
\end{frame}

\begin{frame}[fragile]{Inside the Pipeline (2/2): Raw Scores to a Label}
  \small Continue with these logits: apply softmax, then select the label.
  \[
    \text{Logits}\xrightarrow{\text{softmax}}\text{Probabilities}
    \xrightarrow{\text{largest value}}\text{Label}
  \]
  \begin{lstlisting}[language=Python]
# 4. Convert the two scores into class probabilities.
probabilities = logits.softmax(dim=-1)
for index, probability in enumerate(probabilities[0]):
    print(model.config.id2label[index], probability.item())
# 5. Select the label with the largest probability.
chosen_index = probabilities[0].argmax().item()
print("Prediction:", model.config.id2label[chosen_index])
  \end{lstlisting}
  \begin{itemize}
    \item \texttt{probabilities[0]} selects our one review; its last dimension contains the two classes.
    \item \texttt{config.id2label} maps score positions to labels; \texttt{argmax()} finds the largest value's position.
  \end{itemize}
  \small Compare the label with the one returned by \texttt{classifier(text)}.
  \note{dim=-1 applies softmax over the class dimension. item() converts a scalar tensor into a Python number. Use the same input and model version for the pipeline comparison. The learned architecture and weights are unchanged; we are making the wrapper's steps explicit.}
\end{frame}

\section{Generate Text and Format a Conversation}
\begin{frame}[fragile]{Generate Text: Continue a Prompt}
  \small A \textbf{prompt} is the text we give the model. GPT-2 continues it by choosing a next token, appending it, and repeating --- the loop from Week 1.
  \begin{lstlisting}[language=Python]
generator = pipeline(
    "text-generation", model="openai-community/gpt2",
    device="cpu")
result = generator(
    "A red toy robot",
    max_new_tokens=40, do_sample=False,
    return_full_text=False)
print(result[0]["generated_text"])
  \end{lstlisting}
  \begin{itemize}
    \item \texttt{max\_new\_tokens=40}: stop after at most 40 new tokens.
    \item \texttt{do\_sample=False}: choose the highest-probability token at each step.
    \item \texttt{return\_full\_text=False}: return only the new text, without the prompt.
  \end{itemize}
  \small GPT-2 was trained on web text to predict the next token from the preceding tokens.
  \note{The pipeline manages repeated model calls and turns generated token IDs back into text. return_full_text=False controls the returned text; the model still uses the full prompt as context. If a hypothetical continuation were ``walked across the table.'', False would return that new text alone, while True would return ``A red toy robot walked across the table.'' This is an illustration, not an observed model output. In the notebook, use tokenizer.decode() to do that conversion yourself; model.generate() manages the generation loop directly. This is generation rather than training: the weights stay fixed. Training reference: https://huggingface.co/openai-community/gpt2.}
\end{frame}

\begin{frame}[fragile]{Generation Settings: What Can We Change?}
  \small Compare with the previous call: now choose tokens randomly according to the model's probabilities. This is called \textbf{sampling}.
  \begin{lstlisting}[language=Python]
result = generator(
    "A red toy robot", max_new_tokens=40,
    do_sample=True, temperature=0.7, top_p=0.9, top_k=0,
    return_full_text=False)
  \end{lstlisting}
  \begin{itemize}
    \item \texttt{temperature}: a lower positive value favours the most likely tokens more strongly; a higher value makes the probabilities more even.
    \item \texttt{top\_p=0.9}: keep the most likely tokens until their probabilities total at least $0.9$; sample within that set.
    \item \texttt{top\_k=0}: disable an additional limit on the number of candidate tokens.
  \end{itemize}
  \small In the lab, change one setting at a time and repeat the call. Different wording is not evidence of better or more accurate answers.
  \note{These sampling controls require do_sample=True; temperature must be positive. With do_sample=False and one beam, decoding is greedy. Explain top_k only as disabling an additional default filter here; the notebook uses the same control. More detailed decoding and hallucination explanations remain in Week 1.}
\end{frame}

        \item \textbf{assistant}: the model's reply.

    \end{column}
    \begin{column}{0.52\linewidth}

  \end{columns}

\end{frame}

\section{Measure Quality and Runtime}
\begin{frame}{Where Do the Calculations Run?}
  \small The model's weights and its input arrays must be in memory on the device doing the calculation.
  \par\vspace{0.5em}
  \begin{columns}[T,onlytextwidth]
    \begin{column}{0.47\linewidth}
      \textbf{CPU: the computer's main processor}
      \begin{itemize}
        \item Our examples use \texttt{device="cpu"}.
        \item This is a starting point that works without a separate graphics card.
      \end{itemize}
    \end{column}
    \begin{column}{0.49\linewidth}
      \textbf{GPU: a processor for parallel calculations}
      \begin{itemize}
        \item NVIDIA GPUs: CUDA (\texttt{cuda}).
        \item Supported AMD GPUs: ROCm (also \texttt{cuda} in PyTorch).
        \item Compatible Macs: MPS (\texttt{mps}).
        \item It may speed up inference, but the model and inputs must fit in available memory.
      \end{itemize}
    \end{column}
  \end{columns}
  \par\vspace{0.5em}
  Model weights take space, and the calculation needs additional working memory. A model that downloads successfully may still be too large to run.
  \par\vspace{0.4em}
  \textbf{In the lab}: start on CPU. Try another available device only after the example works, and measure the difference.
  \note{Use one device for the model and inputs in this lab. CUDA, ROCm and MPS are software support for GPU calculations, not models. PyTorch's ROCm build uses the torch.cuda API and the device string 'cuda' for supported AMD GPUs; this does not mean it runs NVIDIA CUDA on AMD. AMD compatibility depends on the GPU, operating system and installed PyTorch/ROCm versions; consult the official support matrix rather than assuming every AMD GPU works. For manual code, model.to(device) and inputs.to(device) move both. Advanced automatic placement, reduced precision and quantization are optional; do not introduce those terms here. References: https://docs.pytorch.org/docs/stable/notes/hip.html and https://rocm.docs.amd.com/en/latest/compatibility/compatibility-matrix.html.}
\end{frame}

\begin{frame}{Batching: Process Several Reviews Together}
  \small A \textbf{batch} is a group of inputs sent through the model in one call. To make a rectangular array, the tokenizer adds \textbf{padding} to shorter inputs.
  \begin{center}
  \begin{tikzpicture}[font=\small]
    \foreach \label/\count/\y in {short review/3/0,long review/8/-0.65} {
      \node[anchor=east] at (-0.2,\y) {\label};
      \foreach \x in {1,...,8} {
        \ifnum\x>\count
          \node[draw=AMU_dk2!40,fill=AMU_dk2!6,minimum width=0.8cm,minimum height=0.5cm] at (\x,\y) {pad};
        \else
          \node[draw=AMU_dk2,fill=AMU_acc5!25,minimum width=0.8cm,minimum height=0.5cm] at (\x,\y) {token};
        \fi
      }
    }
  \end{tikzpicture}
